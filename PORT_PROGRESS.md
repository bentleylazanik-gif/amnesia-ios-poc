### Renderer-specific evidence

- `cLowLevelGraphicsSDL::Init` in `LowLevelGraphicsSDL.cpp` requests SDL `OPENGL`, color/depth/stencil buffers, creates an SDL GL context, and calls `glewInit()`; it does not request an iOS/ES profile. It initializes fixed-function matrices, alpha test, client arrays, and GL state.
- `VertexBufferOGL_Array.cpp` uses client-side vertex arrays; `VertexBufferOGL_VBO.cpp` uses ARB VBOs and unsigned-int index draws. `FrameBufferGL.cpp` uses EXT framebuffer/renderbuffer entry points. `SDLTexture.cpp` contains 1D/2D/3D and compressed texture paths, including formats/calls not available in a minimal iOS backend. `GLSLShader.cpp`/`GLSLProgram.cpp` compile/link GPU programs.
- No shader source files or game materials/textures/meshes are present in this pinned source checkout, so required GLSL versions/extensions and actually reusable materials cannot yet be established. Do not label existing desktop GLSL files “iOS compatible” without an asset/source corpus.
- The abstract `iLowLevelGraphics`/renderer interfaces are a possible seam, but most current capabilities are exposed as desktop GL state operations; implementing a backend means explicit feature mapping, not just linking Metal or renaming OpenGL. The first verifiable HPL2 graphics target should be a backend-owned Metal device/surface and render-target clear, then triangle. A triangle from the current SDL3 color-clear PoC is not an HPL2 renderer milestone.

### HPL2 renderer integration constraints

- `HPL2/core/include/graphics/LowLevelGraphics.h` declares 97 pure-virtual methods across initialization/capabilities, font/GPU-program/texture/vertex-buffer/framebuffer creation, render-target copies/clears, depth/alpha/stencil/blend/scissor/clip state, matrix stacks, texture units/environments, immediate drawing, and vertex batching. `cLowLevelGraphicsSDL` in `HPL2/core/include/impl/LowLevelGraphicsSDL.h` implements this broad interface; it is not a small renderer plugin seam.
- Startup is hardwired: `HPL2/core/sources/engine/Engine.cpp::CreateHPLEngine` handles only `eHplAPI_OpenGL` and creates `cSDLEngineSetup`; `SDLEngineSetup.cpp` creates the SDL system/graphics/input/resource/sound/physics backends and instantiates `cLowLevelGraphicsSDL`. `amnesia/src/game/LuxBase.cpp::InitEngine` explicitly requests `eHplAPI_OpenGL`.
- Even a purportedly simple HPL2 scene is not yet a shader-free Metal triangle: `HPL2/core/sources/graphics/Graphics.cpp` creates and loads `cRendererDeferred`, `cRendererWireFrame`, and `cRendererSimple`; `cRendererSimple::LoadData()` in `RendererSimple.cpp` loads `deferred_base_vtx.glsl` and `deferred_base_frag.glsl`. `LuxBase.cpp` also configures deferred G-buffers. Those shader/asset files are absent from this checkout.
- Resource/data mapping needed for a later Metal backend: `iVertexBuffer` in `graphics/VertexBuffer.h` defines element-array creation, vertex/color/index upload, compile/update, bind/draw/indexed draw, and copies; `iTexture` in `graphics/Texture.h` defines bitmap/raw/cube creation, update, filter/wrap/mipmap and compare state; `iFrameBuffer` in `graphics/FrameBuffer.h` defines 2D/3D/cube color/depth attachments and validation; `iGpuProgram` in `graphics/GPUProgram.h` defines shader linking, sampler/uniform/matrix binding. Desktop implementations are `VertexBufferOGL_Array.cpp`, `VertexBufferOGL_VBO.cpp`, `SDLTexture.cpp`, `FrameBufferGL.cpp`, `GLSLShader.cpp`, and `GLSLProgram.cpp`.
- A credible integration sequence is: introduce a selected graphics-backend seam in engine setup (keep platform, input, resources, sound, physics independently replaceable); create a real `iLowLevelGraphics` implementation without GL; build supported state/buffer/texture/shader paths; route a real HPL2 `iVertexBuffer::Draw` through Metal in a test; then adapt a real HPL2 material and scene. Do not fill the 97 methods with silent no-ops or call that a backend.
